SDK, CLI y worker
Guía técnica

Keepseam mantiene integraciones desde el entorno del cliente: observa contratos, identifica usos potencialmente afectados, prepara propuestas y valida cambios autorizados en copias aisladas. El SDK y la CLI comparten implementación TypeScript.

Alcance entregado: JS/TS, OpenAPI local/HTTPS, evidencia MCP/schema/documentación, propuestas de modelo con consentimiento, revisión semántica, pruebas aisladas y publicación de draft PR separadamente autorizada. El daemon observa y comparte estado opcional; no aprueba cambios. La calidad de un modelo, publicación live y distribución firmada requieren su aceptación específica.
Fuentes aprobadas → evidencia local → impacto JS/TS → propuesta → revisión humana → aprobación de validación → baseline/candidato en Docker → aprobación de publicación → GitHub draft PR → revisión/adopción verificadas por separado Cloud ← únicamente estado permitido y autenticado Modelo / GitHub ← contexto o cambios aprobados directamente

Límites de producto

El código, parches, prompts, schemas privados y logs permanecen locales; el cliente puede autorizar su contexto a un modelo o cambios a su GitHub. Esas rutas no pasan por Keepseam Cloud. Importar el SDK no inicia workers, abre DB, instala herramientas ni ejecuta código consumidor. La funcionalidad local no necesita cuenta Keepseam.

ComponenteContrato
SDK / CLIkeepseam-client, /protocol, /cli; CLI keepseam.
Evidencia / planificaciónSnapshots y hashes, inspección acotada, versiones/procedencia, recetas exactas.
Worker / ejecuciónSQLite privado, jobs y cola con recibos locales; Docker Linux x64 fijo.
Integraciones externasModelo, GitHub y Cloud tienen contratos y permisos independientes.

Un diff estructural no infiere semántica comercial. Un test verde solo demuestra sus aserciones. Una propuesta no equivale a autorización; un draft PR no acredita merge, adopción o despliegue. Las llamadas dinámicas, wrappers/SDK no cubiertos y formatos fuera del perfil permanecen explícitamente sin resolver.

Esta es la documentación técnica mantenida. Fuente: docs/technical-guide.html; PDF: docs/technical-guide.pdf. Las guías de fixtures y laboratorios conservan su alcance de ejemplo, separado del contrato de producto.

Distribución y SDK

El paquete privado keepseam-client@0.1.0 es ESM, UNLICENSED. Requiere Node 24.11.1 ≤ versión < 25; desarrollo usa pnpm 11.19.0. No se ha autorizado publicar en npm. No instalar un paquete ajeno de nombre similar.

Desde el checkout

pnpm install --frozen-lockfile
pnpm engine:setup
pnpm build
pnpm keepseam --help
# Offline solo si las dependencias ya están en el store:
pnpm install --offline --frozen-lockfile

engine:setup descarga oasdiff 1.33.0 oficial, verifica checksum y conserva su licencia en work/tools/oasdiff; necesita tar. Es una adquisición explícita con red. Comparar contratos no descarga el motor automáticamente; se indica su ruta confiable y .exe en Windows.

Instalar el SDK en otro proyecto

pnpm pack --pack-destination work/packages
# En el proyecto receptor, usar la ruta real del archivo:
pnpm add --offline --ignore-scripts /ruta/keepseam-client-0.1.0.tgz
pnpm exec keepseam --help

Packing compila; no publica. El paquete SDK se instala con su runtime/dependencias y no incorpora las fixtures ni oasdiff. Offline exige cache local. Usar imports públicos, sin acoplar consumidores a src/ o dist/; TypeScript usa ESM/NodeNext y tipos Node.

import { compareOpenApi } from 'keepseam-client';
const report = await compareOpenApi({
  basePath: '/contracts/base.json',
  revisionPath: '/contracts/revision.json',
  enginePath: '/opt/keepseam/engine/oasdiff',
});
console.log(report.status, report.changes);

Archivo CLI con runtime incluido

pnpm release:build produce un archivo por plataforma con ejecutable Node SEA, lib/, dependencias materializadas y motor/licencias. Extraer el directorio completo; no requiere Node instalado para la CLI. SDK, supervisor y host Docker conservan sus propios requisitos. El builder verifica help y una comparación real; no acredita publicación remota ni toda la instalación.

Windows no tiene firma Authenticode y macOS solo firma ad hoc, sin notarización. Verificar origen/digest y política de ejecución antes de instalar. Git para publicación debe aceptar git --no-lazy-fetch --version. Observación/propuesta funciona en Windows/macOS; validación consumidor exige Linux x64 y Docker local.

La CLI es pnpm keepseam desde checkout, pnpm exec keepseam desde paquete, o el ejecutable del bundle. Añadir --silent al script pnpm cuando se necesite JSON sin banners. Errores CLI se escriben en stderr; leer el contrato del comando para interpretar sus códigos.

Comparar e inspeccionar

  --engine /opt/keepseam/engine/oasdiff --json

keepseam impact /contracts/base.json /contracts/revision.json \

Las rutas/dominio son placeholders. OpenAPI admite JSON 3.0.x/3.1.x y motor fijado. compare devuelve 0 sin breaking findings, 1 con cambios incompatibles y 2 con input/motor fallido. impact conserva breaking findings incluso si no encuentra un uso consumidor. Todos los informes de impacto requieren revisión.

Inspección sin ejecutar consumidores

scanConsumer y analyzeImpact capturan sintaxis TS/JS y manifests sin importar módulos, resolver imports, ejecutar configuración Babel, instalar dependencias ni lanzar scripts. La evidencia fetch registra ubicación, método/origen conocido y patrón de ruta; soporta segmentos completos /orders/{id}, no parciales como {id}.json.

Lecturas directas de JSON aportan evidencia acotada del parser. Aliases, URLs dinámicas, wrappers, SDK y flujos indirectos pueden quedar sin resolver. Un informe vacío no prueba ausencia de integraciones. Query values y credenciales URL se excluyen; los informes aún contienen metadata privada y no son eventos Cloud.

Fuentes aprobadas · sin crawler

HTTPS, MCP y schemas

http-subscribe registra OpenAPI; source-http-subscribe registra catálogos MCP normalizados, JSON Schema, ejemplos o documentación. Se observa la URL exacta tras opt-in --http; registrar es offline. Sin opt-in se devuelve http-not-enabled y no se presenta una captura fresca.

# Política de ejemplo ficticia, sin credenciales:
{"url":"https://api.example.invalid/openapi.json",
 "allowedOrigins":["https://api.example.invalid"],"contentKind":"json"}
keepseam http-subscribe /private/source-policy.json \
  --baseline /contracts/base.json --consumer /projects/consumer \
  --provider-base-url https://api.example.invalid \
  --engine /opt/keepseam/engine/oasdiff --state /private/keepseam
keepseam worker --once --state /private/keepseam \
  --engine /opt/keepseam/engine/oasdiff --http

HTTPS 443, allowlist exacta, DNS público validado y conexión fijada con TLS por nombre. Rechaza privados/reservados, redirects, compresión, query/fragment/credenciales URL. No usa proxy, cookies, crawl ni retries implícitos. Máximo 4 MiB/30 s, configurable a menos. El SDK permite credenciales por callback para un authContextId opaco; CLI/service solo perfil de fuentes públicas.

Preserva bytes, ETag/Last-Modified y contexto de autorización; 304 reutiliza solo snapshot matching previamente verificado. Captura/cache/comparación/historia se confirman conjuntamente bajo ownership. Un fallo conserva la última evidencia válida; no adelanta freshness. Cambiar alcance de permisos exige otro auth-context.

MCP y JSON Schema

keepseam mcp-compare /captures/before.json /captures/after.json --json
keepseam schema-compare /schemas/before.json /schemas/after.json \
  --direction input --json
keepseam source-subscribe /captures/after.json --kind mcp \
  --baseline /captures/before.json --state /private/keepseam
keepseam source-observe --once --state /private/keepseam --json

MCP exige captura completa, identidad server/protocol/auth-context, capabilities y pagination declaradas. Incompleto o contexto cambiado produce inconclusive; una ausencia no se interpreta como herramienta eliminada. No conecta servidores ni ejecuta tools. mcp-impact --bindings asocia receivers/ficheros explícitos a callTool y lecturas directas de structuredContent; los flujos restantes exigen revisión.

Schema soporta tipo único, propiedades/required/additionalProperties booleano, arrays/items y enum/const scalar. Rechaza refs, combinators, unions y constraints no soportados. Input preserva entradas antiguas; output exige que respuestas nuevas cumplan el contrato viejo. Límites: 4 MiB, profundidad 64, 20.000 nodos; MCP ≤ 1.000 tools. Números con pérdida de precisión son input no soportado.

example-compare y documentación solo muestran evidencia observada: no infieren required fields, variantes o compatibilidad. Texto/HTML no se renderiza ni ejecuta, no sigue links; normalizar saltos es opt-in. Esas fuentes no generan una migración autorizada por sí solas.

Nuevo recorrido de propuesta desde CLI

Proponer con un modelo

Seleccionar un job OpenAPI observado, tests read-only, motor y modelo explícitos. La preparación recomputa diff/impact e inspecciona consumidor actual; no confía en un informe guardado para decidir qué contexto revelar. No se elige ni descarga modelo automáticamente.

# /private/local-model.json: ejemplo de runtime ya instalado
{"provider":"local-openai-compatible","model":"your-installed-model",
 "policyId":"team-local-proposals-v1","maximumOutputTokens":2048,
 "endpoint":"http://127.0.0.1:11434/v1/chat/completions"}
keepseam job-proposal-plan JOB_ID --state /private/keepseam \
  --engine /opt/keepseam/engine/oasdiff --model /private/local-model.json \
  --test orders.test.mjs
keepseam job-propose JOB_ID --state /private/keepseam \
  --engine /opt/keepseam/engine/oasdiff --model /private/local-model.json \
  --test orders.test.mjs --output proposal.json

--source selecciona JS/TS capturado adicional; --evidence añade texto local revisado. Descubrimiento sugiere posibles llamadas/parsers/tests sin seleccionarlos o ejecutarlos. El modelo ve contratos base/revisión completos, impacto y contenidos source/test seleccionados, sin ruta absoluta del consumidor. Inputs demasiado grandes fallan; no se truncan contratos silenciosamente.

--timeout-ms permite 1.000–120.000 ms en plan/propose, por defecto 30.000. El deadline forma parte del request consentido; para una CPU lenta elegirlo explícitamente antes de consentir, sin retries ocultos.

Consentimiento y egress

job-propose imprime el request exacto y exige confirmarlo en terminal interactivo. Consentimiento es de un solo uso y expira; no se recupera deserializando JSON tras reinicio. Un proveedor remoto requiere además --allow-remote. Consentir disclosure no autoriza tests ni GitHub.

Providers: openai, anthropic, google, local-openai-compatible. Config admite solo provider/model/policyId/maximumOutputTokens/endpoint/apiKeyEnv; claves remotas provienen del entorno o del callback SDK. Nunca insertar tokens literales. El endpoint local integrado acepta loopback numérico HTTP; un servidor privado remoto requiere un adaptador autorizado propio.

Loopback no prueba que el runtime no retransmita. Si se exige inferencia privada, fijar pesos/runtime/licencia, aislar red externa, no montar repositorio/credenciales y desactivar telemetría. Revisar contexto para secretos/confidencialidad; patrones y sensitive-values son salvaguardas, no garantía de ausencia.

Resultado honesto

proposal-ready contiene receta no vacía, pendiente de revisión semántica. decision-required contiene preguntas/resumen y ninguna receta: no se fabrica un cambio ni se crea un issue automáticamente. El modelo no puede eliminar preguntas obligatorias del revisor. Contratos/code/docs son datos no confiables, nunca instrucciones con herramientas o permisos.

Se comprueban identidad job, contratos, consumidor y motor antes y después de respuesta. Drift invalida la propuesta. Una operación tiene un intento acotado, sin fallback remoto ni reintentos/expansión de contexto automática. Los tests de transporte con salida controlada no demuestran calidad de inferencia.

Revisar y autorizar

job-propose guarda con escritura exclusiva en state/proposals/ y devuelve artifactPath, proposalSha256 y plantilla de respuestas. Mantener la propuesta original inmutable y privada. Solo una propuesta ready con preguntas sin contestar se puede revisar.

# answers.json: copiar el digest exacto devuelto y todas las preguntas
{"proposalSha256":"SHA256_REAL_DEL_ARCHIVO_PROPUESTO",
 "answers":{"model-semantics":"Respuesta humana con evidencia"}}
keepseam job-review --state /private/keepseam \
  --engine /opt/keepseam/engine/oasdiff \
  --proposal /private/keepseam/proposals/proposal.json \
  --answers /private/answers.json --output reviewed-recipe.json

El JSON es orientativo: debe incluir cada ID obligatorio, incluyendo keepseam-coverage y preguntas de negocio cuando existan. No prellenar respuestas afirmativas. Cada respuesta es texto humano no vacío, ≤ 4 KiB; hash se refiere a los bytes exactos del archivo guardado, no a una serialización alternativa.

job-review valida digest, preguntas e identidad; vuelve a preparar validación y compara evidencia actual. Drift de consumidor, contratos o motor detiene el recorrido. Guarda otra receta, no altera propuesta ni otorga aprobación de tests/publicación.

Receta exacta y plan

Puede proporcionarse una receta propia revisada o la producida por el modelo. plan/createMigrationPlan comprueba hashes y reemplazos únicos sobre posiciones originales, sin solapamiento/cascada, traversal ni cambios en manifests. Un hash identifica contenido; no autentica a un aprobador.

Límites: receta 1 MiB, 50 archivos source, 100 edits/decisions. Pregunta sin respuesta produce requires-decision sin archivos. Ready-for-review sigue authorization: not-granted. JS sintácticamente válido no demuestra typecheck, equivalencia o permiso de ejecución.

keepseam job-plan JOB_ID --state /private/keepseam \
  --engine /opt/keepseam/engine/oasdiff \
  --recipe /private/keepseam/proposals/reviewed-recipe.json \
  --test orders.test.mjs --json
keepseam job-approve JOB_ID --state /private/keepseam \
  --engine /opt/keepseam/engine/oasdiff \
  --recipe /private/keepseam/proposals/reviewed-recipe.json \
  --test orders.test.mjs

job-approve presenta cambios, tests y recursos; requiere escribir el request ID exacto, sin --yes ni autorización piped. Un SDK caller explícito puede usar approveJobValidation bajo su propia política; no debe invocarlo automáticamente desde una respuesta modelo/Cloud no confiable.

El recibo se liga a estado, job, consumidor, contratos, receta, tests y perfil. Expira en 15 minutos y es de un uso. Cambios materiales exigen revisar de nuevo. Una negativa o pregunta de semántica no se elimina para hacer pasar tests.

Perfil fijo Linux x64

Exige /usr/bin/docker, daemon local /var/run/docker.sock y la imagen Node previamente adquirida. Docker Desktop, socket remoto/rootless, servicios de aplicación, instalaciones y scripts de package arbitrarios están fuera del perfil. Windows/macOS devuelve blocked; jamás ejecuta consumidor directamente en host.

Resultados conservados

passed: baseline/candidato pasan; improved: falla baseline y pasa candidato; regression: falla solo candidato; failed: ambos fallan. Infraestructura ausente, límites, cleanup no confirmado o ejecución incompleta produce blocked. Publicación solo admite candidato passing con evidencia durable y cleanup confirmado.

CLI ejecución devuelve 0 sin trabajo o todo passed, 1 con fallos completados/improvement y 2 blocked/interrupted/lost-ownership. Completed significa resultado registrado, incluso blocked. No modificar tests válidos ni borrar marcadores para reusar un recibo. El checkout original permanece intacto; reporte y output son privados.

Draft PR y reconciliación

Seleccionar antes de observar un repo consumidor independiente, committed, root exacto no-bare SHA-1 con .git local. Fixtures internas no cumplen este perfil. Preflight compara source/manifests capturados con index y blobs HEAD crudos en ambas direcciones; rechaza cambios no confirmados del perfil, worktrees, submodules, objetos externos o configuración peligrosa.

keepseam publication-plan INTENT_ID --state /private/keepseam \
  --git /usr/bin/git --engine /opt/keepseam/engine/oasdiff \
  --repository OWNER/REPO --base main --json > /private/candidate.json
keepseam publication-review --candidate /private/candidate.json \
  --author-name "YOUR NAME" --author-email "YOUR EMAIL" \
  --github --json > /private/publication-request.json
keepseam publication-approve --request /private/publication-request.json \
  --state /private/keepseam --consumer /projects/consumer
keepseam publication-publish --request /private/publication-request.json \
  --state /private/keepseam --consumer /projects/consumer \
  --approval PUBLICATION_RECEIPT_ID --github --json

Review solo lee GitHub y verifica repo privado, activo/writable/no-fork, immutable ID, permisos y base/tree exactos. GH_TOKEN se resuelve al request; preferir credencial corta y scope de un repo. La aprobación local presenta contenido/destino y exige request ID exacto; recibo propio 15 minutos/one-use, distinto del de tests.

El adapter crea blobs/tree/commit inmutables, una rama create-only feat/api-… y un draft PR same-repository GitHub.com. No sobrescribe ramas ni commits humanos, mergea o despliega. Revalida source y base; cambios de identidad/permiso/conflictos detienen writes. Races humanos pueden existir alrededor de crear PR; la comprobación no es un CAS atómico remoto.

Interrupciones y efectos inciertos

keepseam recover-approved --state /private/keepseam --json
keepseam publication-reconcile --request /private/publication-request.json \
  --state /private/keepseam --consumer /projects/consumer \
  --approval PUBLICATION_RECEIPT_ID --github --json

Execution conserva intención antes de create, ID antes de start, journal con labels/hashes y outcome después del resultado. Recovery verifica ownership y contenedores por ID, puede completar evidencia o cleanup; nunca inicia tests ni devuelve un interrupted intent a cola. Creación incierta sigue cleanup-unresolved aunque no se vea aún un contenedor.

Publicación guarda intención durable antes de cada write. Timeout/respuesta perdida produce uncertain, sin retry automático. Reconcile es read-only: reconoce PR matching abierto/cerrado/merged y conserva cambios humanos; una PR ausente no prueba que el write no vaya a terminar. Mantener request/recibo/journal original. Simulation no acredita una PR real.

SQLite, archivos, Docker y GitHub no comparten transacción atómica ni garantía exactly-once. No mover/importar estado entre hosts como recuperación, borrar marcadores o editar DB. Un PR no cambia automáticamente baseline/adopción/deployment; esa reconciliación de contenido requiere aceptación propia.

Persistencia local y freshness

Observación y estado

keepseam subscribe /contracts/revision.json --baseline /contracts/base.json \
  --consumer /projects/consumer --provider-base-url https://api.example.invalid \
  --engine /opt/keepseam/engine/oasdiff --state /private/keepseam
keepseam worker --once --state /private/keepseam \
  --engine /opt/keepseam/engine/oasdiff --json
keepseam subscriptions --state /private/keepseam --json
keepseam jobs --state /private/keepseam --json

Baseline/configuración se captura de forma inmutable; observar B no convierte B en versión adoptada. Repetir registro igual es idempotente. Jobs se deduplican por subscription, contratos, consumidor y motor; cambios de consumidor crean nueva evidencia, rollback conserva historia. Bytes cambiados pueden requerir review aunque no haya breaking findings.

El estado debe estar fuera del checkout y no contenerlo. Node SQLite usa transacciones/sincronización y leases con owner/generation; commit obsoleto es rechazado. En Node 24.11.1 SQLite es experimental; usar patch LTS compatible y conservar backup privado. No usar un filesystem compartido/remoto ni editar filas para saltar permisos.

AlmacénContenido y límites
worker.sqlite3100 subscriptions, 1.000 jobs/transitions; contratos/reports ≤ 4 MiB, totales snapshots/reports 64 MiB cada uno.

Son límites de payload, no de tamaño exacto de DB. No hay pruning automático; agotamiento falla sin borrar evidencia o fingir freshness. Cambios de schema propios se migran transaccionalmente, conservando historia; DB ajena/futura falla. Ownership observer dura cinco minutos; ejecución diez y recovery cinco.

Permisos y diagnóstico

POSIX: directorios 0700/archivos 0600. Windows: nuevas carpetas reciben DACL privada; paths existentes inapropiados fallan sin repair implícito. Rechazar symlinks/junctions, hardlinks runtime y directorios de red. La misma cuenta OS y administradores forman parte del trust boundary; modos/ACL no autentican un revisor humano.

Una observación fallida preserva último éxito/jobs y registra razón fija. worker --once devuelve 0 sin job actual pendiente, 1 con review y 2 busy/failure; unchanged no cierra jobs históricos. Plan/propuesta usan último snapshot capturado y no consultan proveedor silenciosamente; observar de nuevo antes de decidir y revisar timestamps.

worker-loop permite ciclos finitos y, solo con opt-in, ejecutar recibos ya aprobados. El servicio persistente observa, crea jobs y sincroniza metadata; jamás genera consentimiento, responde preguntas semánticas, ejecuta consumidor ni publica por sí solo.
